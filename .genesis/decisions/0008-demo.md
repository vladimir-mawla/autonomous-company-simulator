# ADR 0008 — M8 demo: one page that offers events to the real engine and renders only what comes back, one bridge that is the only file to touch `lib/` and `domains/`, and a diff against `npm run demo:company` that a test does

- **Date:** 2026-11-09
- **Status:** proposed — written by the builder; not yet approved by an independent L4 pass
- **Phase / milestone:** M8 (BUILD) — `app/page.tsx`, `app/globals.css`, `app/milestones.ts`, `app/milestones.test.ts`, `components/company/**` (`compute-demo-view.ts`, `format-standing.ts`, `format-breach.ts`, `format-rejection.ts`, `format-attempt.ts`, `CompanyDemo.tsx`, `__tests__/`)

The sabotage ledger and the timings below were measured on the tree of commit `1cc4d8b`. Every commit after it changes this ADR only (`git diff 1cc4d8b..HEAD --stat -- app components lib domains scripts tests package.json package-lock.json` prints nothing; checked at the end of the build). The ledger quotes "N failed" and the files they were in, with no count of passing tests, which goes stale whenever a test is added. The counts under "Coverage" are counts of what a test or a command did on that tree.

## Context

`.genesis/PLAN.md` §6 (M8) asks for one page that drives the real engine in the browser: one pure bridge, one `useReducer`, no `useEffect`, `useCallback`, `useMemo`, `setTimeout` or `async`; a seq scrubber; "Revoke Ops-Lead"; three overreach presets; "Autonomous quarter (seed N)"; the org tree with `limit / used / headroom`; the commitments table with standings; the attempt transcript with named rejections; a conservation meter; and `app/milestones.ts` with a drift guard against `.genesis/DONE.html`. It must refuse to render a standing, heir or rejection the engine did not just produce for the log on screen, to throw, and to show a different number from `npm run demo:company`. M8 owns the paths above and edits nothing under `lib/`, `domains/`, `scripts/` or `tests/`; `git diff origin/main..HEAD --name-only` lists only M8's paths and this file. No dependency was added (`package.json` and `package-lock.json` are untouched; `npm ci` was the only install command). ADRs 0001 to 0007 describe the layers underneath and are cited, not restated.

## Decision 1 — what the page opens on, and what "the canonical log" means for the plan's checks

`app/page.tsx` stays a server component; `CompanyDemo` is the one client boundary. The page **opens on plan §7 as it stood just before the revoke**: the ten admitted events of seq 1 to 10 and the eleven refusals of beat 1, offered to the engine one step at a time (`initialDemoState`, 21 calls). "Revoke Ops-Lead" then offers the revoke of seq 11 (the script's own `revoke-G2` step, by `cfo`). "Replay the whole incident" offers all 33 steps (`replayScript()`).

The plan's check (2) says "clicking 'Revoke Ops-Lead' on the canonical log renders the same table as the last block of `npm run demo:company`". Two readings of the words are possible and this ADR states the one taken: the revoke is part of the canonical script, so a page that opened on the full log would have nothing to click. The page therefore opens before it, and the check is read as: the standings table before and after the click, and at seq 18 and scrubbed to seq 10, are the script's four standings blocks, and the autonomous quarter's numbers are the script's last block (the quarter's per-policy lines, its counts and its oracle line). `__tests__/demo-diff.test.tsx` does the diff (Decision 6).

The three presets offer the script's own steps: "Widen scope" is `widen-scope` (`capability-widening { hire }` against the opening log), "Over-delegate" is `over-delegate` (`over-allocation { G2, requested 200000, headroom 50000 }`), "Spend beyond limit" is `c8` with an id of its own per press (`ui-c-<n>`, because pressing it twice would otherwise offer one id twice and meet `duplicate-id`): admitted at seq 11 and ruled `void: over-limit { G6, 50000, 28000 }`. They are the domain's steps, not events built in the page. The attempt type's `source` is `"canon"` for them and for the revoke (the domain's `AttemptSource` has no "visitor"; it is the domain's type and is not changed here).

## Decision 2 — state, and one deviation from the plan's wording

The component holds one `useReducer`. The plan says its state is `{ log, attempts }`. It is, plus two fields that are the page's own and not the engine's: `cursor` (the scrubber, `null` is the live head) and `seed` (the number in the quarter box). A scrubber and a seed box need a value that survives a render, and the alternative (a second `useState`) would break "single `useReducer`". Nothing the engine said is held twice: `log` and `attempts` are what `append` returned through `offer`, and everything shown is `computeDemoView(state)` folded again from the log on every render.

The reducer lives in the bridge, because it calls `offer`, `replayScript` and `runQuarter`. Every action returns to the live head (`cursor: null`) except `scrub` and `set-seed`. "Autonomous quarter" replaces the log with `runQuarter(seed, 60)`; 60 ticks and seed 1 are the numbers `scripts/demo-company.ts` uses (`DEMO_TICKS`, `DEMO_SEED`), and `demo-diff.test.tsx` fails if the script's header line says otherwise. The one engine answer the reducer does not use is a non-null `fault` from `runQuarter` (it keeps the state it had); `append` cannot produce one, and the domain's own tests run 200 seeds.

## Decision 3 — one bridge, and what that means for the formatters

`components/company/compute-demo-view.ts` is the only file of M8 that imports `lib/**` or `domains/**`, and only through their barrels. The formatters and the component take their types from it (`export type { Breach, Rejection, Standing, Attempt, ... }`), so the type-only imports of `format-*.ts` run from the bridge and the bridge imports nothing from them: there is no runtime cycle. The formatters' `switch`es end in a function whose parameter is `never`, so a kind added to `Breach`, `Rejection` or `Standing` is a compile error there and not a blank cell.

`format-attempt.ts` is **not in the plan's list** of files (`compute-demo-view.ts`, `format-standing.ts`, `format-breach.ts`, `format-rejection.ts`, `CompanyDemo.tsx`, `__tests__/`). It is inside `components/company/**`, which M8 owns. It holds the words for one call (what was offered, and the engine's answer), which belong to none of the three. This is an addition, recorded here, not a replacement.

The mechanical form of "only the bridge" is `__tests__/source-scan.test.ts` with `__tests__/support/scan.ts` (Decision 7).

## Decision 4 — what the bridge computes, and the two arithmetics it does

`computeDemoView(state)` returns `{ ok: true, view } | { ok: false, error }`. The checks that can fail are explicit and each returns an error: a cursor outside the log; a transcript whose admitted calls are not exactly the log's events (a state that is not one story); a log the engine cannot replay (`fold`'s own `FoldFault`, as text); a standing for a commit not in the log; a grant the engine does not know. A `try/catch` is the second layer. Tests: `compute-demo-view.test.ts`, the group "computeDemoView never throws, and says why when it has no view" (a position outside the log, a transcript that is not the log's story, a log the engine cannot replay, anything the checks did not foresee: a log that throws when read).

Everything in the view is read off a value the engine returned: the standing of each commit (`standings`), whether a grant is live (`domains/company`'s `makeOrgView`, which reads `lib/chain`), `used` and `headroom` per grant (`usedOf`, `headroomOf`), `absorbed` for a grant that was revoked (`absorbedBy`), the heir, `severed` and `chargedTo` inside the standing. Two things are arithmetic, both named by the plan, and both are in this file and nowhere else:

- **`returned`**, one subtraction: the revoked grant's limit less `absorbed` (plan §8 A: "the UI-needed `absorbed`/`returned` ← `absorbedBy` + `grant.limit`"; `scripts/demo-company.ts` prints the same subtraction as `returned = limit(G2) 400000 - absorbed`). G1's headroom, which the engine gives, is what rises by it (500 000 to 680 000), and the test pins both.
- **the conservation meter**, a sum of the amounts of the commits ruled `binding` or `inherited` against a sum of the root grants' limits. The plan asks for it by that formula and the engine has no function that returns it, so the bridge adds the numbers up. It is an observer, as the script's oracle is: nothing reads it to decide anything. It is cross-checked in the exhaustive test against two sums that do not use it: the amounts of the commits the fold's own record calls `warranted`, and the sum of the engine's `charges`. It is **not** the engine's `usedOf`, which counts what a grant has handed down as well as what was spent.

This is a departure from "no computation in the UI" in the strict sense and is stated as one: the brief for this milestone asks that computation run through the engine and the domain, and these two sums are the only places a number is made here that the engine did not hand over. They are small, they are named in the type, and `compute-demo-view.test.ts` pins their values (232 000, 242 000, 375 500 of 1 000 000; 220 000 and 180 000).

## Decision 5 — the scrubber folds the prefix, and shows the calls up to it

At seq `k` the view is built from `log.slice(0, k)`: `fold`, `standings` and `makeOrgView` are called on that prefix, so a revoke after `k` cannot reach it (the test that, for every `k` from 0 to 18, the scrubbed view equals the view of a state whose log stops there). The transcript shows the calls up to and including the one the engine admitted at `k`; refusals that came after it are hidden, and at `k = 0` there are none. At seq 10 of the whole incident `c1 c2 c3 c4` are all `binding`; at 11 `c1 c2 c4` are `inherited`, heir `cfo` (`compute-demo-view.test.ts`, the scrubber group), and the rendered table at seq 10 is the script's "scrub back to seq 10" block (`demo-diff.test.tsx`).

## Decision 6 — the diff against `npm run demo:company` is a test

The plan says "an independent verifier diffs the two", and DONE.html's gate says the live demo and the script "produce the same standings, diffed by the verifier". `__tests__/demo-diff.test.tsx` does that mechanically, so it cannot go stale: it runs `scripts/demo-company.ts` the way `npm run demo:company` does (once, when the file is loaded), reads the script's four standings blocks (before the revoke, after it, at seq 18, scrubbed to seq 10), renders the page with `renderToStaticMarkup` at the state each is of, reads the "Who answers" table back out of the markup (commit id, seq, kind and the engine-literal detail text) and compares the lines one by one with the script's. It also compares: `absorbed = 220000`, `returned = limit(G2) 400000 - absorbed = 180000`, `G1 headroom: 500000 -> 680000`; and, for the quarter (the script's last block), the five per-policy lines, the line "the quarter's log: 118 admitted events; standings binding x44 inherited x3 void x39" and the oracle line "root G1: 375500 bound of a limit of 1000000". The page's "detail" cell is `format-standing.ts`'s `detail`, which is the text the script prints after the kind, character for character; the human sentence ("cfo answers for it, charged to G1") is in its own element above it.

What the diff is, said exactly: two programs that share the engine and the domain, and not each other's code (the script has its own expectation table typed from plan §7), agree on those lines. It is not a pixel comparison and it is not run against the deployed URL; see "Not verified".

## Decision 7 — the scan of the page's own source, and what it cannot see

`__tests__/support/scan.ts` walks the syntax tree of every `.ts` and `.tsx` file of `components/company/` (not `__tests__/`) plus `app/page.tsx` and `app/milestones.ts`. It reports: an identifier or string literal spelt as a banned hook or timer (`useEffect`, `useLayoutEffect`, `useInsertionEffect`, `useCallback`, `useMemo`, `setTimeout`, `setInterval`, `requestAnimationFrame`, `queueMicrotask`), wherever it stands (a call, an import specifier, `React.useMemo`, a destructuring, `React["useCallback"]`); `async`, `await` and `Promise`; any hook but `useReducer`; `Date`, `performance`, `crypto`, `fetch`, `window`, `document`, `navigator`, `localStorage`, `sessionStorage`, `process`, `globalThis` and `Math.random`; any module reference (import, export-from, dynamic `import()`, `require`, import type, `/// <reference>`) that resolves into `lib/` or `domains/` from any file but the bridge, or from the bridge to anything but one of the five barrels; the engine's function names appearing as identifiers outside the bridge; a module reference that is not a repository file, `react`, `react-dom` or `next`; and an inventory (non-source file, symlink, parse failure).

It does **not** see, and each of these is planted and shown not reported in the test file (`THE BLIND SPOTS`): a name built at run time (`"use" + "Effect"`, a template with a substitution, `[...].join("")`), `Reflect.get`, a computed key whose value is not a literal, a dynamic `import("react")` followed by a computed read, and any file outside the scanned set (`app/layout.tsx` is one). A green result says the forms it lists are absent from the files it lists, and nothing about the evasions.

The scan has teeth: one planted violation per rule form in a synthetic tree, exactly those `file:rule` pairs reported, beside controls (a `useReducer`, look-alike names such as `useless` and `timeout`, `Math.trunc`, plain strings) that are not. The real source has no finding, the scan parsed the eight files it is about, and the bridge is the only scanned file that imports the engine.

## Decision 8 — the drift guard, and what a mark-done pull request must now update

`app/milestones.ts` lists the nine milestones with a `status` (`done`, `in-progress`, `planned`); `app/page.tsx` reads it and writes no milestone number into prose. `app/milestones.test.ts` reads `.genesis/DONE.html`'s status table (each row's id and the text of its last pill) and asserts that **the set of milestones claimed done is the same in both**. It does not compare the not-done states (`todo`, `wip` against `in-progress`, `planned`), as in decision-engine's guard it ports. It asserts that nine rows were found, in order (so a reshaped table is red, not vacuous), and has teeth: a page with one pill flipped in either direction and a module with one status flipped are reported by id.

**This is the part a later pull request must know.** In M8's own pull request M8 is `in-progress` in the module and `todo` in DONE.html, so the guard is green. A `chore(genesis): mark MN done` pull request must, **in the same pull request**:

1. flip MN's pill in `.genesis/DONE.html` (`pill todo` / `todo` to `pill ok` / `done`), as every mark-done pull request already does;
2. flip MN's `status` in `app/milestones.ts` to `"done"` (the bookkeeping exception of PLAN.md §6 names "status lines in `app/milestones.ts`"), and, if the next milestone becomes the current one, nothing else: `currentMilestone()` and the page follow from the statuses;
3. update `.genesis/checkpoints/CURRENT.md` as before.

If only one of 1 and 2 is edited, `app/milestones.test.ts` is red on that pull request (its TEETH tests show each direction). The mark-done pull request for M9 sets the last status to `done`, after which `currentMilestone()` is `undefined` and the page says all nine are done (`app/page.tsx` handles it; `app/milestones.test.ts` asserts that a current milestone is never one that is done, and is all nine if there is none).

## Decision 9 — the exhaustive check, and the one shortcut it takes

Plan check (1): every sequence of length at most 4 over the page's button alphabet yields `ok: true` and a conserving view. The alphabet has eight buttons: Revoke Ops-Lead; Widen scope; Over-delegate; Spend beyond limit; Autonomous quarter; the seed box set to 2; Replay the whole incident; Reset. 8 + 64 + 512 + 4096 = 4 680 sequences, each from the opening state through the real reducer, split into 8 sequences of length 1 and 64 subtrees of 73 (one per first two buttons) so that each test stays small. At every sequence the test asks `computeDemoView` for the live view and one scrubbed back from the head (and, for sequences of length at most 3, also at seq 0 and at the middle), and checks: `ok`; the meter holds, and equals the amounts of the commits the fold calls warranted, and equals the sum of the engine's `charges`, both computed in the test from the raw log; the head is the log's length; one standing per commit; the counts are the rows; no live grant has `used` over its limit and no grant has negative headroom; the live view shows every call.

The one shortcut: "Autonomous quarter" takes 26 ms a call and 585 of the 4 680 sequences end in one, so the test computes it once per seed through the real reducer and reuses the result. That is sound only if the quarter depends on the seed alone, and a test asserts it ("is independent of what was on screen before it": the state after `quarter` from a state with a revoke, a spend and a replay on it equals the state after `quarter` from the opening state). Sequences that continue from a quarter then call the real reducer on it.

"Conserving" here means what the test lists; it is not a proof for every log, which is unbounded (the plan says so: "the finite-state analogue ... since the log is unbounded").

## Decision 10 — look, accessibility and layout, and how each was checked

`app/globals.css` holds the page's styles with colours as tokens on `:root`, redefined under `prefers-color-scheme: dark`; the page follows the visitor's system theme (there is no toggle). Standings and statuses carry their meaning in words as well as colour (`binding`, `inherited`, `void`, `live`, `revoked at seq 11`, `cut off`, `the bound holds`). Landmarks and headings: one `h1`, a `h2` per section, `section aria-labelledby`, a `caption` on each table (screen-reader only), `th scope`, labelled seed and scrubber inputs with `aria-valuetext`, `role="status" aria-live="polite"` on the latest-answer box and the time-travel line, scrollable regions focusable (`tabindex="0"`) and named, buttons at least 44 px tall, `:focus-visible` outlines. Bars are native `<progress>` with an `aria-label` that spells limit, used, headroom and status. Long ids wrap (`overflow-wrap: anywhere`) and tables scroll inside their own region, never the page.

Checked by hand in the browser pane, on the production build (`next build --webpack` then `next start`) and on `next dev --webpack`: at 375 px wide, light theme, `document.documentElement.scrollWidth` equals `innerWidth` (375) and no element's right edge is past the viewport; at 900 px in dark theme, the bound, the tree after the revoke (G2 revoked at seq 11 with 220,000 absorbed and 180,000 returned, G4 and G5 cut off) read correctly; on `next dev` the console shows no hydration warning or error after load and after every click. The click path was exercised by script in the page: Spend beyond limit (the latest answer reads "admitted at seq 11, void: over-limit"), Revoke Ops-Lead (the standings become inherited, inherited, binding, inherited), setting the scrubber to 10 and 13 through the input's native setter and an `input` event (binding x4, then the head), Back to live, Autonomous quarter (the meter reads 375,500 against 1,000,000 and the transcript has 155 calls) and Reset (binding x4). These are observations of one session and are **not pinned by a test**: `vitest` stays `environment: "node"`, so the click-to-re-render path has no automated test (the plan's disclosed gap, kept); the reducer and the view it feeds are what the exhaustive test covers, and the rendered markup at six states is what the render test covers.

Not measured: layout shift (no content is inserted after load, and the first render is the server's markup, so none is expected; no Lighthouse or CLS number was taken), contrast ratios (the tokens were chosen to be legible in both themes and looked at, not computed), and any browser but the one in the pane.

## Coverage, and how long the tests take

On the tree of `1cc4d8b`: `npm run typecheck` clean, `npm run lint` clean, `npm test`: 70 test files and 1 858 tests passed (the repository was 64 files and 1 657 tests before M8). M8's part is 6 files and 201 tests: `compute-demo-view.test.ts` 107 (of which 73 are the exhaustive subtrees), `format.test.ts` 37, `CompanyDemo.render.test.tsx` 26, `source-scan.test.ts` 12, `demo-diff.test.tsx` 11, `app/milestones.test.ts` 8.

Timing: three full-suite runs, then one under 20 `yes > /dev/null` (killed afterwards; `pgrep -x yes` printed 0), `vitest run --reporter=json`, on a laptop whose one-minute load average from other jobs was between 8 and 12 (it was not idle). Slowest M8 test: 251 ms, 164 ms and 180 ms in the three runs, and 623 ms under load, which is 12% of vitest's 5 s default; the slowest of the whole suite in the same runs was an M3 test (`attenuation-closure.test.ts`, which carries its own 60 s timeout) at 2 321, 2 420 and 2 203 ms and 11 532 ms under load. **No M8 test has an explicit timeout.** (`demo-diff.test.tsx` runs the script with `spawnSync(..., { timeout: 60000 })` when the file loads; that is a process limit, not a test timeout, and the script takes about 0.3 s.) The exhaustive check is split into 73 tests so that none is slow; `compute-demo-view.test.ts` as a file takes 5.2 to 5.8 s in the quiet runs and 21.7 s under load for its 107 tests, and vitest has no per-file limit.

## Not verified, and what is stated and not pinned by a test

- **The click path has no automated test** (the plan's disclosed gap). It was exercised by hand in the browser pane against the production build and the dev server (Decision 10); the live URL is checked after merge and recorded by M9 in `docs/WALKTHROUGH.md`.
- **Hydration**: that the server's markup and the browser's first render match is observed (no console warning on `next dev` after load and after clicks), not tested; the test is that the markup is a function of the state and that two renders of one state are one string.
- **Layout shift, contrast, other browsers, Lighthouse**: not measured (Decision 10).
- **The page against the deployed URL**: this milestone is verified on a local build and a fresh clone; the Vercel preview of the pull request is reported in the pull request after CI, and the deployed `main` after merge.
- **The 90-second tour's prose** ("dana gave the cfo...", "the bound meter does not move", "seq 10") is written text about the opening log, not rendered from the engine. The numbers in it are limited to "seq 10", and the behaviours it names are pinned by `compute-demo-view.test.ts` (the meter does not move after "Spend beyond limit"; the four are binding at seq 10); the sentences themselves are not tests.
- **The meter is an observer** (Decision 4); the scan for "the page never rules" claims only the forms listed in Decision 7.
- **`demoReducer` never throws** is evidence for the 4 680 sequences, not a proof for every state.
